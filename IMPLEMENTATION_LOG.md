Corrigido fixando `APP_URL=http://localhost` em `phpunit.xml` (junto dos outros overrides que já existiam para `DB_DATABASE`, `SESSION_DRIVER`, etc.) — os testes devem ser herméticos em relação a qualquer valor do `.env` real, e essa lacuna específica nunca tinha sido coberta porque, até agora, nenhum `.env` real usado neste projeto tinha um path no `APP_URL`.

## 2026-08-15 — Deploy real testado com o prefixo `/visitas/` (não só configurado)

O usuário confirmou que `public_html` já hospeda outro site — este app fica em `public_html/visitas/`, subpasta. Ajustei `index.php`/`.htaccess` (movidos, path relativo +1 nível), `bootstrap/app.php` (`usePublicPath` para `public_html/visitas`) e `vite.config.js` (build de produção passa a exigir `VITE_BASE_PATH=/visitas/`). Ao testar isso **de ponta a ponta com o prefixo de verdade** (não só checando status HTTP), apareceram dois bugs reais que nenhum teste anterior pegava, porque todos rodavam com `base: '/'` (raiz):

**Bug 1 — estrutura de pastas incompatível com o `base` do Vite.** Minha primeira tentativa copiou o build para `public_html/visitas/build/` (mantendo a rota de fallback `public_path('build/index.html')` que já existia). Mas o Vite, com `base: '/visitas/'`, gera HTML referenciando `/visitas/assets/index-xxx.js` — **sem** o segmento `/build/`. Testei isso com `curl` checando só o status HTTP (200) e achei que estava certo; só quando chequei o **conteúdo real** da resposta (`curl` do JS retornava o HTML do fallback SPA, não o JS) que percebi o engano — o pedido de asset caía no catch-all do Laravel por não encontrar o arquivo físico no lugar certo. Corrigido eliminando a subpasta `build/`: o conteúdo do build agora fica direto em `public_html/visitas/`, junto com `index.php`/`.htaccess`; `routes/web.php` mudou para `public_path('index.html')`. Lição: **checar status HTTP não é o mesmo que checar que o conteúdo certo voltou** — um 200 "errado" (fallback SPA servido no lugar de um asset) passa despercebido se você só olha o código de status.

**Bug 2 — `api.js` fazia redirect absoluto sem o prefixo.** Depois de corrigir a estrutura de pastas, o app carregava mas ficava em branco. Rastreei via `page.on('pageerror')`/`page.on('console')` do Playwright (em vez de só checar HTTP): o interceptor de resposta do Axios tinha `window.location.href = '/login'` hardcoded para tratar 401/423 — isso é uma navegação de página cheia, **fora** do react-router, e portanto nunca ganhava o `basename="/visitas"` que o `BrowserRouter` aplica às navegações internas. Toda vez que `/api/auth/me` retornasse 401 (o caso NORMAL de "ainda não logado", que acontece em todo carregamento inicial do app), o navegador era mandado pra `http://dominio/login` (raiz) em vez de `http://dominio/visitas/login` — 404 imediato. Isso é um bug que **sempre existiu**, só nunca tinha aparecido porque todo teste anterior desta sessão rodava com `base: '/'` (onde `/login` e `/visitas/login` coincidem). Corrigido extraindo `frontend/src/lib/basePath.js` como fonte única do prefixo (usada tanto pelo `basename` do `BrowserRouter` quanto pelos redirects do `api.js`), garantindo que os dois nunca divirjam de novo.

Ferramentas usadas para achar isso: `vite preview` (que respeita `base` de verdade, ao contrário de servir os arquivos estáticos direto) para o lado do frontend, e `php artisan serve` com `usePublicPath` apontando pra a pasta certa para o lado do Laravel — junto com Playwright capturando console/pageerror, não só screenshots. Validado depois de corrigido: fluxo completo (login → troca de senha → dashboard → refresh numa rota profunda) mantendo `/visitas` na URL o tempo todo.

## 2026-08-15 — Revisão de segurança independente (seção 132 do PRD) e correções

Um agente sem contexto prévio do desenvolvimento auditou os 20 itens da seção 132, lendo o código real (não presumindo nada) e validando empiricamente os pontos críticos (rodou `migrate:fresh` contra um SQLite descartável, testou regras de validação em runtime, inspecionou o `sw.js` compilado). Resumo do relatório e das correções aplicadas nesta sessão:

**Achado #16 (ALTO) — timezone.** `config/app.php:68` tinha `'timezone' => 'UTC'` hardcoded em vez de `env('APP_TIMEZONE', 'UTC')` — o `.env` já definia `APP_TIMEZONE=America/Sao_Paulo`, mas era silenciosamente ignorado. Toda a aplicação operava 3h adiantada. Maior impacto: `DailyRoundController::todaysRound()` usa `now()->toDateString()` como eixo de "hoje" — a partir das 21h BRT, `round_date` já virava o dia seguinte, e como `daily_rounds` tem `UNIQUE(admission_id, round_date)`, uma visita real registrada na manhã seguinte colidiria com o registro da noite anterior e sobrescreveria `completed_by`/`completed_at`. **Corrigido** com `env('APP_TIMEZONE', 'UTC')`; teste de regressão (`TimezoneConfigTest`) trava a config para não regredir silenciosamente de novo.

**Achados #14 (MÉDIO) — reinternação.** Dois problemas relacionados: (a) `AdmissionController::restore()` não revalidava se o paciente já tinha outro episódio ACTIVE antes de restaurar um excluído — cenário: médico exclui episódio A por engano, cria episódio B, admin restaura A pela tela de excluídos → paciente fica com dois ACTIVE simultâneos, quebrando o invariante que `Patient::activeAdmission()` e todo o resto do sistema assume. (b) A checagem de duplicidade em `store()` ficava **fora** da transação, abrindo uma janela TOCTOU entre duas requisições `POST /api/admissions` simultâneas para o mesmo paciente. **Corrigido** movendo a checagem para dentro da transação, adicionando validação equivalente em `restore()`, e — a garantia de última linha — uma migration com índice único parcial `CREATE UNIQUE INDEX admissions_one_active_per_patient ON admissions(patient_id) WHERE status='ACTIVE' AND deleted_at IS NULL` (SQLite suporta índices parciais nativamente). Ambos os controllers agora capturam `UniqueConstraintViolationException` e convertem para uma mensagem amigável. 2 testes de regressão.

**Achado #15 (MÉDIO) — snapshot de plano dessincronizado.** `AdmissionController::update()` só recalculava `health_plan_name_snapshot` quando `payer_type` vinha junto na mesma request. Enviar só `health_plan_id` (sem `payer_type`) passava na validação (`payer_type` é `'sometimes'`) mas não caía em nenhum dos dois ramos do `if/elseif` — o snapshot ficava preso no plano antigo enquanto `health_plan_id` já apontava pro novo. Como dashboard e exportação usam o snapshot preferencialmente, indicadores por convênio ficariam errados. **Corrigido**: recalcular sempre que `health_plan_id` estiver presente em `$data`, independente de `payer_type`. Teste de regressão.

**Achado #8 (MÉDIO) — `.env.example` inseguro.** Ainda era o stub padrão do Laravel (`APP_NAME=Laravel`, `SESSION_DRIVER=database`, `CACHE_STORE=database`), sem `SESSION_SECURE_COOKIE`/`HTTP_ONLY`/`SAME_SITE` nem `APP_TIMEZONE`. Risco: `session.secure` lê `env('SESSION_SECURE_COOKIE')` sem default — a chave ausente vira `null`, cookie de sessão sem flag Secure se alguém copiar `.env.example` direto pra produção. **Reescrito** para refletir produção segura por padrão (`APP_DEBUG=false`, `SESSION_SECURE_COOKIE=true`, etc.), com comentário explícito de qual valor sobrescrever para dev local sem HTTPS.

**Achado #20.1 (MÉDIO) — sessão sobrevive à desativação.** `AuthController::login` só valida `active=true` no momento do login; o `SessionGuard` depois só relê o usuário do banco, nunca revalida `active`. Desativar um médico (`Admin\UserController::deactivate`) não derrubava a sessão dele — continuaria com acesso a PHI até expirar por inatividade (o que pode ser "nunca", já que `SESSION_LIFETIME` renova a cada requisição). **Corrigido** com um middleware novo, `App\Http\Middleware\EnsureUserIsActive` (alias `active`), aplicado junto com `auth` em `routes/web.php` — se `$user->active === false`, faz logout + invalida a sessão + retorna 401 na própria requisição que descobriu isso. Optei por não usar o `AuthenticateSession` nativo do Laravel porque ele exige coluna `remember_token`, que este schema não tem (decisão de design: sem "lembrar-me" numa aplicação clínica). Teste de regressão simula: login, uma chamada OK, desativa via update direto no model, próxima chamada → 401 + `assertGuest()`.

**Achado #20.2 (MÉDIO) — fallback SPA aponta pro lugar errado.** `routes/web.php` usa `public_path('build/index.html')`, mas como `bootstrap/app.php` nunca chamava `usePublicPath()`, isso resolvia pra `equipe/app/public/build/index.html` — que não existe no deploy real (o build vai pra `public_html/build`, documentado em `DEPLOYMENT_HOSTGATOR.md`). Consequência: `/` funcionaria (Apache serve o arquivo físico), mas F5 ou deep link em qualquer subrota do SPA devolveria o texto "Frontend ainda não compilado" com HTTP 200. **Corrigido** chamando `$app->usePublicPath(dirname(__DIR__, 3).'/public_html')` em `bootstrap/app.php` — a estrutura de pastas do dev espelha exatamente a de produção (`public_html` e `equipe` sempre siblings), então o mesmo caminho relativo funciona nos dois. **Validado de verdade**: buildei o frontend, copiei pra `public_html/build`, subi `php artisan serve` e confirmei com `curl` que tanto `/` quanto `/admin/dashboard` (rota profunda) servem o `index.html` corretamente.

**Achados baixos, todos corrigidos:**
- `PatientController` não tinha Policy nenhuma (`lookup`/`store`/`history` sem `authorize()`). Não era explorável hoje (só 2 roles, ambas com acesso igual), mas uma terceira role futura herdaria acesso a PHI por omissão. Criada `PatientPolicy` (retorna `true` pros 3 métodos, documentando a decisão) e conectada nos 3 métodos do controller.
- `HealthPlanPolicy`/`MedicalSpecialtyPolicy::viewAny` retornavam `true` incondicionalmente — as rotas `admin.health-plans.index`/`admin.medical-specialties.index` (listagem completa, inclusive inativos) ficavam acessíveis a qualquer PHYSICIAN apesar de estarem sob `/admin`. Corrigido pra `$user->isAdmin()` — o autocomplete público (`/health-plans/search`) não passa por Policy nenhuma e continua aberto de propósito.
- Reautenticação por senha em `forceDestroy`/`resetClinicalData` não tinha rate limit — um atacante com uma sessão de admin sequestrada tinha um oráculo de senha ilimitado. Novo limitador `reauth` (5/min por usuário), aplicado nas duas rotas.
- Throttle de login só por usuário+IP permitia testar a senha padrão (`senha@1234`) contra centenas de contas do mesmo IP sem nunca bater no limite. Adicionado um segundo `Limit` só por IP (20/min) — `RateLimiter::for()` aceita um array de `Limit`s, todos são aplicados.
- `AuditLogger` fazia `hash('sha256', $ip)` sem salt — espaço IPv4 é só 2^32, rainbow table completa em minutos. Trocado por `hash_hmac('sha256', $ip, config('app.key'))`.
- `AuditLogger` gravava `X-Request-Id` do cliente direto no banco sem validar formato — um valor forjado podia poluir a trilha de auditoria (ex.: imitar o request_id de outra operação). Agora só aceita se `Str::isUuid()` validar; caso contrário gera um novo.
- `UpdateAdmissionRequest`: a regra `'hospital_discharge_at' => [..., 'after_or_equal:admission_at']` era um no-op silencioso — `admission_at` não é campo desta request (só existe em `StoreAdmissionRequest`), então o Laravel comparava contra `null` e nunca bloqueava nada. Permitia gravar alta hospitalar anterior à entrada via `PUT`. Corrigido com uma closure comparando contra `$this->route('admission')->admission_at` (o valor já persistido). Teste de regressão.
- `DailyRoundController::assign` validava só `exists:users,id` — aceitava atribuir o responsável do dia a um usuário desativado. Corrigido com `Rule::exists('users', 'id')->where('active', true)`. Teste de regressão.

**Confirmado seguro sem alterações** (o núcleo, essencialmente): rotas sem autenticação (nenhuma encontrada fora do login), IDOR nos controllers com route model binding (todos chamam `authorize()` antes de qualquer efeito), CSRF (toda a API dentro do grupo `web`, nenhuma exclusão), XSS (zero `dangerouslySetInnerHTML`/`innerHTML` no frontend, CSP restritiva no backend), SQL injection (zero `whereRaw`/`DB::raw` com input do usuário — as 2 únicas ocorrências são `PRAGMA` literais), mass assignment (zero `$request->all()` em todo o backend), soft delete respeitado por padrão em todas as queries de dashboard/exportação, hard delete corretamente exclusivo de ADMIN, backups/exports fora de `public_html` com nome não previsível, concorrência SQLite (WAL + busy_timeout + transações curtas), migrations rodando limpas.

Depois de aplicar todas as correções: 51 testes passando (7 novos de regressão, um por achado testável), confirmado sem dependência de ordem com `--order-by=random` 2x, Pint limpo, e um teste de fumaça completo no navegador (login → novo atendimento → dashboard admin → planos → sistema/integrity_check) sem nenhum erro de console além dos esperados.

## 2026-08-15 — Restore, Zona de Perigo e arquivos de deploy

- Restore é **exclusivamente CLI** (`neurologia:restore`), nunca uma rota web — decisão direta da seção 95 do PRD, que permite essa saída quando o restore via navegador não pode ser feito com segurança. Trocar o arquivo `.sqlite3` por baixo de uma aplicação com PHP-FPM rodando é um risco real (outros workers podem manter conexões abertas para o arquivo antigo); só faz sentido correr esse risco com acesso direto ao servidor.
- Extraído `App\Services\BackupService` de dentro do comando `neurologia:backup` (que virou um wrapper fino de CLI) para ser reusado pela Zona de Perigo — ambos precisam da mesma garantia de "backup verificado antes de qualquer coisa destrutiva".
- **Decisão de design**: `BackupService` resolve o caminho do banco via `config('database.default')` em vez de hardcodar `'sqlite'` — isso não é só um detalhe de teste, é mais correto em geral (se a conexão padrão mudar de nome no futuro, o serviço continua funcionando).
- **Bug de teste encontrado e corrigido** (não afeta produção): para testar o fluxo feliz da Zona de Perigo, era preciso um SQLite em arquivo de verdade (o backup de segurança precisa copiar um arquivo real, não `:memory:`). A primeira tentativa mudou `database.connections.sqlite.database` e chamou `DB::purge('sqlite')` — isso destruiu a conexão `:memory:` compartilhada que o `RefreshDatabase` do Laravel mantém viva por TODA a execução do PHPUnit (é assim que ele evita re-migrar a cada teste), quebrando ~20 testes de outras classes que rodam depois em ordem alfabética. Corrigido registrando uma conexão nomeada separada (`sqlite_danger_zone_test`) e trocando só `database.default` temporariamente, sem nunca purgar a conexão `sqlite` original. Confirmado sem dependência de ordem rodando a suíte duas vezes com `--order-by=random`.
- `public_html/index.php` e `.htaccess` reais (não só documentados) — copiados do padrão do `public/index.php`/`.htaccess` do Laravel, com os caminhos ajustados para carregar `equipe/app` de fora de `public_html`. Documentada explicitamente a incerteza sobre se `visitas` será o document root dedicado (como o diagrama da seção 5 do PRD sugere) ou uma subpasta dentro de um `public_html` compartilhado com outro conteúdo do domínio — isso muda a profundidade dos `../` e se `VITE_BASE_PATH` precisa ser usado no build; só dá pra decidir com acesso real ao cPanel.
- Testado visualmente e funcionalmente via Playwright: criação de paciente/episódio real, `integrity_check` retornando "ok", zona de perigo executada com sucesso (backup de segurança aparece na lista de backups, paciente some do dashboard).

## 2026-08-15 — Dashboard, exportação XLSX e PWA

- **Dashboard de indicadores**: `App\Http\Controllers\Admin\DashboardController` calcula tudo em PHP sobre a Collection já filtrada (não em SQL agregado) — volume razoável para um único serviço hospitalar, e evita reescrever a mesma lógica de negócio (ex: "tempo de acompanhamento = closed_at ?? now() menos started_at") em SQL cru duplicado. Percentis via `App\Services\Percentiles` porque SQLite não tem `PERCENTILE_CONT`.
- Extraído `App\Services\AdmissionFilters` a partir do dashboard para ser reusado pela exportação — evita as duas features divergirem silenciosamente sobre o que "período X, médico Y, CID Z" significa.
- **Bug encontrado e corrigido** (visual, via screenshot): "patient-days (Neurologia)" aparecia como `0.000029902511574074073` — soma de frações de dia sem arredondamento. Corrigido com `round(..., 1)`.
- **Exportação XLSX**: `phpoffice/phpspreadsheet` precisou de `ext-gd` e `ext-zip`, que existiam no XAMPP mas estavam desabilitados no `php.ini` — habilitados. Download entregue por rota autenticada com `deleteFileAfterSend(true)` — mas o cliente de teste HTTP do Laravel não chama `Response::send()`/`sendContent()` (só o ciclo real via SAPI faz isso), então o teste automatizado de "arquivo é apagado após o download" precisou disparar `sendContent()` manualmente no `BinaryFileResponse` subjacente para provar o comportamento; confirmado também com download real via navegador (arquivo some da pasta `equipe/exports` depois do download).
- **Gotcha de ambiente (Windows + OneDrive)**: durante o `composer require` do PhpSpreadsheet, `php artisan` começou a falhar com "bootstrap/cache directory must be present and writable" mesmo com a pasta existindo e sendo gravável de fato. Causa: o OneDrive/Explorer tinha marcado a pasta com o atributo `ReadOnly` (efeito colateral inofensivo do Windows, não uma ACL real), e `is_writable()` do PHP no Windows confia nesse atributo em vez de checar permissão de escrita de verdade — mesma classe de bug já visto no `neurologia:preflight`. Corrigido com `attrib -R` recursivo nas pastas do projeto. Sem relevância para produção (Linux/cPanel).
- **PWA**: `vite-plugin-pwa` com `generateSW`, `globPatterns` restrito ao shell estático, `runtimeCaching: []` e `navigateFallbackDenylist: [/^\/api\//]` — deliberadamente sem nenhuma regra que toque `/api`, para não depender de "lembrar" de excluir rotas clínicas do cache no futuro. Ícones (192/512/512-maskable/apple-touch-icon) gerados via GD como placeholder (fundo azul + "N") já que não há arte de marca real disponível — documentado como pendência de troca antes do lançamento.
- Validação real (seção 116 do PRD): build de produção servido via `vite preview` (com `preview.proxy` adicionado no `vite.config.js`, já que `server.proxy` não se aplica ao preview), Playwright aguardando o service worker ficar `active` de verdade, login real, criação de paciente/episódio real via `fetch()`, e inspeção de `caches.keys()`/`localStorage`/`indexedDB.databases()`. Resultado: só os 10 arquivos do shell no Cache Storage, nenhuma entrada `/api/*`, nenhum rastro do nome/prontuário criado, localStorage vazio, nenhum banco IndexedDB.

## 2026-08-15 — Frontend React (fluxo assistencial principal)

- Sem framework de UI (Material/Tailwind/etc.) — CSS próprio mobile-first em `index.css`, seguindo a diretriz do PRD de visual limpo/hospitalar sem excesso de dependências.
- Autenticação: `AuthContext` consome `/api/auth/me` no mount para restaurar sessão; `ProtectedRoute` decide entre login/troca de senha obrigatória/rota normal/admin-only puramente a partir do objeto `user` — nenhuma lógica de autorização real vive no frontend (é só UX; o backend já rejeita com 403/423 independentemente do que a UI decide mostrar).
- Cliente axios usa `withXSRFToken: true` (Axios lê o cookie `XSRF-TOKEN` que o Laravel seta automaticamente em qualquer resposta do grupo `web`) — não precisa de Sanctum nem de um endpoint dedicado de "csrf-cookie".
- **Decisão de arquitetura de dev**: Vite roda em porta separada do `php artisan serve`; configurado proxy `/api → 127.0.0.1:8000` em `vite.config.js` para o navegador enxergar tudo como mesma origem (senão cookie de sessão cross-origin não funcionaria em dev sem reconfigurar CORS/SameSite).
- **Achado durante o teste E2E**: no Windows, o Vite dev server só ficou acessível via `localhost` (resolve para `::1`/IPv6), não via `127.0.0.1` diretamente — `curl http://127.0.0.1:5173` dava "connection refused" enquanto `curl http://localhost:5173` funcionava. Sem relevância para produção (Linux/cPanel), mas relevante para quem for rodar `npm run dev` localmente nesta máquina.
- **Achado importante para o deploy**: a URL de produção é `drfernandofreua.com.br/visitas` — uma subpasta, não a raiz do domínio. Isso quebra os caminhos absolutos de assets do build do Vite (`/assets/...`) se o document root do domínio não apontar direto para essa pasta. Adicionado suporte a `VITE_BASE_PATH` (env var) em `vite.config.js` + `basename` correspondente no `BrowserRouter` (via `import.meta.env.BASE_URL`), para poder buildar com `VITE_BASE_PATH=/visitas/ npm run build` quando necessário — decisão real fica para a FASE 20, quando a estrutura exata do cPanel for confirmada.

## 2026-08-15 — Backend FASES 2 a 10 (parcial 12/16)

- **Users**: reescrita da migration padrão do Laravel para o schema do PRD (`uuid`, `full_name`, `crm`, `username`, `role`, `must_change_password`, `active`, `last_login_at`) — sem `email`, sem tabela `password_reset_tokens`/`sessions` no banco (`SESSION_DRIVER=file`, sem fluxo de reset por e-mail, admin reseta senha diretamente).
- Removidas as migrations de `cache`/`jobs` do Laravel padrão: `CACHE_STORE=file` e `QUEUE_CONNECTION=sync` (execução síncrona, sem worker residente) tornam essas tabelas desnecessárias — alinhado com a restrição de "sem processos residentes" do PRD.
- Migrations criadas na ordem de dependência correta (health_plans, medical_specialties, cid10, patients, admissions, admission_diagnoses, pending_items, daily_rounds, audit_logs) — todas testadas com `migrate:fresh`.
- `Admission` usa `SoftDeletes` real do Laravel + coluna `version` para optimistic locking (`assertVersion()` lança `StaleAdmissionException` → 409). O hook `updating` incrementa `version` automaticamente a partir do valor original carregado do banco.
- **Bug encontrado e corrigido**: colunas com apenas default no banco (`version`) ou nunca atribuídas em memória (`first_neurology_evaluation_at`, etc.) ficavam ausentes do JSON de resposta do `store()` porque `Model::create()` não repopula atributos a partir de defaults do SQL — corrigido com `$admission->refresh()` após criar, e com `$admission->version ??= 1` explícito no hook `creating`.
- Autenticação: sessão/cookie Laravel padrão (guard `web`), sem Sanctum — todas as rotas de API ficam dentro do grupo `web` do `routes/web.php` (não `routes/api.php`) propositalmente, para ganhar CSRF + sessão automaticamente já que o frontend é mesma origem. Rota SPA fallback (`GET /{any}`) serve `public_html/build/index.html` para o roteamento client-side.
- RBAC via Policies do Laravel (auto-discovery por convenção de nome), não por checagem manual de `role` espalhada pelos controllers.
- `App\Http\Controllers\Controller` do Laravel 12 vem **sem** `AuthorizesRequests`/`ValidatesRequests` por padrão (mudança do skeleton) — precisou adicionar os traits manualmente, senão `$this->authorize()` não existe.
- **Bug encontrado e corrigido**: `DailyRoundController` usava `firstOrNew(['round_date' => ...])` comparando string exata, mas o cast `date` do Eloquent serializa com componente de hora ao salvar (`2026-08-14 00:00:00`), quebrando o lookup e causando `UNIQUE constraint failed` ao tentar completar uma visita logo após atribuir o responsável do dia. Corrigido usando `whereDate()` para a busca (robusto a variações de formato) e `make()` explícito quando não encontrado.
- **Bug encontrado e corrigido**: algoritmo de retenção de backups (diário/semanal/mensal) tinha uma condição de corrida entre faixas — um backup já mantido pela faixa diária era pulado ao calcular o "dono" do balde semanal, permitindo que um backup mais antigo roubasse aquela vaga semanal por engano. Corrigido calculando os representantes de cada faixa de forma independente (por recência dentro do balde) e só then mesclando os conjuntos — coberto por teste unitário dedicado (`BackupRetentionPolicyTest`).
- `neurologia:backup`: `PRAGMA wal_checkpoint(TRUNCATE)` antes de copiar o arquivo (nunca copiar um `.sqlite3` "cru" com WAL ativo), checksum SHA-256, retenção configurável via `config/neurologia.php`.
- `neurologia:preflight` e `neurologia:backup` usam `App\Services\DirectoryWriteCheck` (escreve e remove um arquivo de teste) em vez de `is_writable()`, que é conhecidamente pouco confiável para diretórios no Windows — necessário porque o ambiente de desenvolvimento é Windows mas a produção é Linux/cPanel.
- 25 testes automatizados cobrindo os cenários críticos das seções 107-114 do PRD (login/RBAC, prontuário único, reinternação sem sobrescrever plano anterior, avaliação única, soft/restore/hard delete com RBAC real via API, reset diário do responsável, optimistic locking). Laravel Pint limpo.
